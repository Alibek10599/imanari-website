One file describes the whole app.

Imanari is a small language for declaring an app's data, actions, screens, limits, recovery and repair in one place. The compiler turns it into a native Rust backend and a browser UI, and checks that what you declared is what runs.

The reference app, annotated

This is examples/fieldwork/fieldwork.nr, exactly as it ships. Two users create, list and complete their own tasks. The marked lines are the ones the compiler and runtime hold you to. Point at a note to see the block it explains.

imanari "0.1";app fieldwork {  targets = [web];  identity development {    mode = local_dev;  }
  entity Task {    owner_field = owner;    // id and revision are supplied by the runtime.    field title {      type = Text;      min_length = 1;      max_length = 200;    }    field owner {      type = UUID;    }    field completed {      type = Bool;      default = false;    }  }

Every task belongs to a user. Generated queries are scoped to the signed-in owner, so one user can never read or change another user's tasks.

  action create_task {    kind = insert;    entity = Task;    access = signed_in;    input title {      type = Text;      min_length = 1;      max_length = 200;    }    set = {      title: @input.title,      owner: @actor.id,    };  }

The owner comes from the session, never from the request body. Inputs are checked against their declared bounds before any SQL runs.

  action list_tasks {    kind = list;    entity = Task;    access = signed_in;  }
  action complete_task {    kind = update;    entity = Task;    access = signed_in;    input id {      type = UUID;    }    input revision {      type = Int;    }    id = @input.id;    expected_revision = @input.revision;    set = { completed: true };  }

Updates check the record's revision. A stale write gets a conflict instead of silently overwriting someone else's change.

  screen tasks {    route = "/";    title = "My tasks";    query = list_tasks;    form add_task {      submit = create_task;      input title {        label = "Task title";        placeholder = "What needs doing?";      }    }    list task_list {      source = @query.items;      fields = [title, completed];      button complete {        label = "Mark complete";        action = complete_task;        arguments = {          id: @item.id,          revision: @item.revision,        };      }    }  }

Screens are built from native browser controls and bound to actions. A button can only call what its action allows.

  runtime local {    bind = "127.0.0.1";    port = 7331;    database = ".nari/app.db";    request_limit_bytes = 65536;    request_timeout_ms = 5000;  }

Limits live in the source. The runtime enforces body size, timeouts and per-user rate limits on every request.

  recovery backend_process {    target = backend;    max_restarts = 3;    window_seconds = 60;    backoff_ms = [100, 500, 2000];    after_exhaustion = stop;  }

A separate supervisor restarts the backend within this budget. When the budget runs out, it stops and tells you instead of looping.

  repair local_candidate {    mode = isolated;    max_attempts = 2;    editable_actions = [complete_task];    automatic_release = false;  }

When a protected test fails, Imanari proposes a fix and validates it in a sandbox. It may edit only these actions, and nothing ships until you apply it.

What nari build writes

Everything the compiler produces lands in .nari/ next to your source. The IR and graph are deterministic and hashed, so the same source always gives the same output. Agents read a bounded context for the one node they are changing, not the whole project.

.nari/
├── ir.json             typed IR with semantic and source hashes
├── graph.json          every node and the edges between them
├── generated/app/      Rust backend on Axum, for SQLite or PostgreSQL
├── generated/web/      browser UI built from native controls
├── generated/runtime/  the runtime the backend links against
├── build/              the compiled backend
├── context/<node>/     bounded context for changing one node
└── deploy/plans/       reviewed deployment plans, named by hash

Releases you can read first

nari plan builds a Docker image and writes down everything the release will do: the image digest, resources, schema changes, readiness rule and a dated cost estimate. The plan is named by its hash. nari release applies exactly that plan, or refuses if the source, image or target changed since you read it.

nari plan --database-url-env DATABASE_URL
nari release <plan hash>
  1. Start. The new version boots next to the running one, on the same database.
  2. Check. It has to report ready and pass a health check inside the private network.
  3. Switch. The proxy reloads and sends traffic to the new version, then confirms it answers.
  4. Retire. The old version drains for five seconds and stops.

If the new version never gets ready, traffic never moves. If it fails after the switch, the proxy routes back. Schema changes are additive, so both versions work against the same database while they overlap.

Install

Imanari compiles apps with Cargo, so install Rust with rustup first. Generated apps pin their own Rust version, and rustup fetches it on the first build.

macOS, Apple silicon

curl -fsSL https://github.com/Alibek10599/imanari/releases/latest/download/imanari-aarch64-apple-darwin.tar.gz | tar -xz
sudo install imanari-aarch64-apple-darwin/nari /usr/local/bin/nari

All releases

Your first app

nari init hello
cd hello
nari dev

nari dev builds the app, starts it under the supervisor, and prints a one-time link that signs you in as a local development user. The first build compiles the backend's dependencies and takes about a minute.

What Imanari does not do yet

Mobile targets, workflows, external adapters, native extensions and canary releases come in later releases. Declaring any of them today fails with a diagnostic instead of being quietly ignored. Deploys go to a single Docker engine, and schema changes that remove, rename or retype stored data are refused rather than guessed.

Sandboxed repair needs macOS. On Linux, repair stops after static validation and reports that no sandbox is available.
