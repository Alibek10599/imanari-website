One file describes the whole app.

Imanari is a small language for declaring an app's data, actions, screens, limits, recovery and repair in one place. The compiler turns it into a native Rust backend and a browser UI, and checks that what you declared is what runs.

What nari build writes

Everything the compiler produces lands in .nari/ next to your source. The IR and graph are deterministic and hashed, so the same source always gives the same output. Agents read a bounded context for the one node they are changing, not the whole project.

.nari/
├── ir.json             typed IR with semantic and source hashes
├── graph.json          every node and the edges between them
├── generated/app/      Rust backend: Axum and SQLx on SQLite
├── generated/web/      browser UI built from native controls
├── generated/runtime/  the runtime the backend links against
├── build/              the compiled backend
└── context/<node>/     bounded context for changing one node

Install

Imanari compiles apps with Cargo, so install Rust with rustup first. Generated apps pin their own Rust version, and rustup fetches it on the first build.

macOS, Apple silicon

curl -fsSL {{DL}}/imanari-aarch64-apple-darwin.tar.gz | tar -xz
sudo install imanari-aarch64-apple-darwin/nari /usr/local/bin/nari

All releases

Your first app

nari init hello
cd hello
nari dev

nari dev builds the app, starts it under the supervisor, and prints a one-time link that signs you in as a local development user. The first build compiles the backend's dependencies and takes about a minute.

What Imanari does not do yet

For now Imanari runs on your own machine. Mobile targets, production sign-in, PostgreSQL, migrations, workflows and deploys come in later releases. Declaring any of them today fails with a diagnostic instead of being quietly ignored.

Sandboxed repair needs macOS. On Linux, repair stops after static validation and reports that no sandbox is available.
